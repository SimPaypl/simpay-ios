# SimPay Mobile SDK contract

Language independent description of how every SimPay Mobile SDK must behave: the native
Android (Kotlin) and iOS (Swift) SDKs and the Flutter and React Native adapters built on
them. The contract is data, not code: JSON files read by a small conformance runner in
each SDK. There is no shared business logic and no Kotlin Multiplatform.

Status: **draft, contract version 1.0.0**. Not published.

## Layout

```
Contract/
├── contract.json                     manifest: contract version, bridge format version, file index
├── codes/codes.json                  stable error codes, pending reasons, result types (with meaning)
├── api/
│   ├── status-mapping.json           API transaction status -> flow outcome
│   ├── http-error-mapping.json       HTTP status x endpoint -> error code + failure kind
│   ├── transport-error-mapping.json  network failure x endpoint -> error code + failure kind
│   └── fixtures/channels-example.json
├── validation/
│   ├── order-validation.json         order input (bridge form) -> valid | error code
│   └── amounts.json                  amount grammar, JSON serialization, display
├── policy/
│   ├── session.json                  provider, expiry, 401 handling, bridge session decoding
│   ├── blik.json                     BLIK Level 0 flow, code format, rejection limit
│   ├── polling.json                  intervals, budget, read outcomes, lifecycle
│   ├── retry.json                    failure kinds, which requests may ever be repeated
│   ├── outcome-unknown.json          when the outcome is unknown and what follows
│   └── return-urls.json              payment page checks, return URL matching
├── bridge/bridge-v1-examples.json    normative examples of adapter payloads
├── schema/
│   ├── bridge-v1.schema.json         JSON Schema of every bridge message
│   └── scenario.schema.json          JSON Schema of a conformance scenario
└── scenarios/*.json                  end-to-end checkout scenarios (one file each)
```

Entries may carry `androidToday`: what Android SDK 1.0.0 (commit `00216f5`) does when it
differs from the contract. It is informational. The Android runner reports such entries
as *known divergences* instead of failures until the Android SDK is aligned.

## Scenario format

A scenario is one checkout run against a scripted API (`schema/scenario.schema.json`):

| Field | Meaning |
|---|---|
| `id`, `title`, `covers` | Identifier (= file name), description, covered behaviours |
| `order` | bridge-v1 order fields overriding the default order (49.99 PLN, `payer@example.com`) |
| `session.payerIp` | Payer IP of the fake session (`null` = none). Tokens are generated by the runner |
| `api.<endpoint>` | Replies per endpoint (`channels`, `create_transaction`, `submit_blik_code`, `transaction_status`), consumed in order, the last one repeating. A reply is `{status, headers?, json?}` or `{transportFailure}` |
| `steps` | User and system actions: `load_channels`, `select_channel`, `submit_blik_code`, `back_to_channels`, `lifecycle`, `run_polling`, `close`; `accepted: false` when the action must be refused |
| `expect.result` | The single final result in bridge-v1 form (`error.message` is not compared) |
| `expect.requests` | Exact transport calls per endpoint. `create_transaction` and `submit_blik_code` (the mutating requests) are mandatory in every scenario |
| `expect.transactionCreatedEvents`, `expect.sessionRequests` | Optional counters |

`run_polling` advances a manual clock through every poll interval until the checkout
finishes or the polling budget ends, so no runner ever waits for real time.

## Test data

Synthetic only: tokens `mobsdk_test_*` (generated by runners, never stored in files),
e-mails under `example.com` (RFC 2606), IPs from TEST-NET ranges (RFC 5737). The iOS test
`No real tokens, e-mail addresses or IP addresses in the contract` enforces this for
every file.

## Versioning

`contract.json.contractVersion` follows Semantic Versioning, independent of SDK versions:

| Change | Version |
|---|---|
| New scenario, new case in an existing table, new optional field, new error code, new pending reason | minor |
| Clarified wording, `androidToday` notes, typo | patch |
| Changed expectation of an existing case, removed or renamed code, changed meaning, changed scenario format | major |

Rules:

- Codes, pending reasons and result types are never renamed or reused; `since` records
  the contract version that introduced them.
- Each SDK declares the contract version it conforms to (in its release notes) and runs
  the conformance suite of exactly that version in CI.
- `bridgeFormatVersion` (`version` in every bridge payload) changes only with an
  incompatible payload change and is independent of `contractVersion`.
